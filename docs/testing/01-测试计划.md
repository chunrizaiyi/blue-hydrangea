## 1. 测试对象与范围

以仓库当前源码和已有功能为依据，覆盖花园首页、我视角下的他、今日花语、情绪解语、我们的回忆、今日心情、纪念日、横屏专注时钟和白噪音。跨模块关注本地数据升级与保留、异常恢复、权限、后台与锁屏行为、隐私边界、动画与音频体验。

本阶段只执行已有 Dart 测试及静态检查。AI 真接口、Android 系统通知、锁屏提醒、摄像头、耳机和长时间播放需要后续阶段的自动化或真机执行；不能用本阶段结果宣称这些行为已经通过。

## 3. 风险与优先级

| 等级 | 判定原则 | 本项目典型场景 |
| --- | --- | --- |
| P0 | 数据丢失、敏感信息泄露、核心计时错误或主要功能无法完成 | 旧版升级后回忆丢失；AI 密钥出现在日志；倒计时锁屏后延迟提醒 |
| P1 | 主要操作错误，但可通过重新操作恢复 | 新增后列表不刷新；日期筛选错误；通知操作不同步 |
| P2 | 不影响数据和主流程的视觉或文案问题 | 动画抖动、布局重叠、白噪音接缝可感知 |

执行顺序为 P0 → P1 → P2。本轮设计的 60 条用例中，P0 为 16 条，P1 为 39 条，P2 为 5 条。缺陷严重程度与用例优先级分别记录：低优先级场景也可能暴露高严重程度缺陷。

后续计时真机验收拟在已授予精确提醒及通知权限的条件下，分别重复短倒计时和 45 分钟倒计时至少 3 次，记录计划到点与提醒开始的系统时间；单次延迟超过 10 秒列为待分析问题。未授予权限、系统节电策略或设备差异单独记录，不与上述条件混算。白噪音循环在接缝前后各截取至少 10 秒音频并进行听感复核；动画记录屏幕录像及逐帧检查，性能阶段再补充帧耗时分布。上述数值是后续测试的判定方案，不属于本阶段已取得的结果。

测试数据使用虚构人名、示例图片、假 API 响应和无效测试密钥。不得把真实私人记录、有效密钥、签名文件或未脱敏的设备日志上传到 GitHub。

## 5. 执行与缺陷流程

1. 为每条用例记录执行日期、设备、安装包版本、结果（通过／失败／阻塞）和证据位置；未运行的用例标记为“待执行”。
2. 失败时先稳定复现，再记录最短复现步骤、预期、实际、日志或截图、严重程度和影响范围。
3. 在 GitHub Issue 记录缺陷，关联修复提交与回归用例；关闭前在原设备复测，必要时增加其他设备回归。
4. 每次阶段结束发布测试报告，给出执行总数、通过数、失败数、阻塞数、未执行数及遗留风险。没有测到的内容不能写为“通过”。

后续发布候选版本的结束条件：全部 P0 用例完成并通过；P1 失败项完成风险评估和回归安排；不存在未处置的数据丢失、敏感信息泄露或计时失准缺陷；测试报告与代码版本、设备环境一一对应。阶段一只评估测试设计和基线，不按该发布条件判定产品质量。

统计口径：

- **需求设计覆盖率**＝至少关联一条用例的需求数 ÷ 已列需求数；只衡量设计是否遗漏，不表示功能通过。
- **用例通过率**＝通过数 ÷（通过数＋失败数）；阻塞与未执行单列，不纳入分母。
- **关键流程自动化率**＝已自动化并可重复运行的 P0/P1 流程数 ÷ 计划自动化的 P0/P1 流程数。
- **缺陷关闭率**＝完成修复和回归的缺陷数 ÷ 已确认缺陷数；未确认问题不计入。
